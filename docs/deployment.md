# БЛОК 1: Базовая настройка сервера

## Шаг 1.1: Подключение к VM

```bash
ssh root@<YOUR_IP>
```

### Что это делает
Подключаешься по SSH к свежей VM в Yandex Cloud как root (единственный пользователь на новой машине).

### Альтернативы
| Вариант | Как | Когда использовать |
|---------|-----|-------------------|
| **SSH по ключу (сейчас)** | `ssh -i ~/.ssh/id_rsa root@<IP>` | ✅ Стандарт — более безопасно, чем пароль |
| **SSH по паролю** | `ssh root@<IP>` (интерактивно вводишь пароль) | Если ещё нет SSH-ключа (редко) |
| **Консоль Yandex Cloud** | Прямо в веб-интерфейсе — кнопка "Подключиться" | Если SSH не работает, нужна диагностика |

### Почему выбран SSH по ключу
- **Безопаснее:** ключ хранится только на твоём ноутбуке, передаётся не открытым текстом
- **Удобнее:** не нужно вводить пароль каждый раз
- **Стандарт индустрии:** все production-серверы используют ключи
- **Защита от перебора:** пароль подобрать можно (brute-force), ключ из 2048 бит — нельзя

## Шаг 1.2: Создание пользователя `deploy`

```bash
adduser deploy && usermod -aG sudo deploy
```

### Что это делает
1. `adduser deploy` → создаёт новый пользователь с домашней папкой `/home/deploy`
2. `usermod -aG sudo deploy` → добавляет его в группу `sudo` (может выполнять команды с `sudo`)

### Альтернативы
| Вариант | Команда | Когда использовать |
|---------|---------|-------------------|
| **useradd вместо adduser** | `useradd -m deploy` | Если adduser недоступен (редко). adduser — дружелюбнее (интерактивный) |
| **Работать только от root** | Просто `sudo` до конца | ❌ Опасно! Одна ошибка может стереть весь сервер |
| **Несколько пользователей** | `adduser app` для приложения, `adduser backup` для бэкапов | Если разграничивать доступ по приложениям (усложнение) |

### Почему выбран этот вариант
- **Безопасность:** если хакер взломает приватный ключ или приложение, у него будут права только `deploy`, а не root
- **Разделение ответственности:** root — только для критических операций, повседневная работа от обычного пользователя
- **Unix-принцип:** каждый пользователь отвечает за свой процесс (Postgres под user `postgres`, Next.js под `deploy` и т.д.)

### Важный момент
После `adduser deploy` интерпретатор спросит пароль и дополнительную информацию. Пароль можно оставить пустым (нажать Enter), потому что логиниться будешь по SSH-ключу, не по паролю.

## Шаг 1.3: Копирование SSH-ключей

```bash
rsync --archive --chown=deploy:deploy ~/.ssh /home/deploy
```

### Что это делает
Копирует содержимое папки `~/.ssh` (SSH-ключи root) в `/home/deploy/.ssh` с правильными правами доступа.

**Структура:**
```
~/.ssh/
├── id_rsa              # Приватный ключ (СЕКРЕТНЫЙ!)
├── id_rsa.pub          # Публичный ключ
└── authorized_keys     # Ключи, которым разрешено логиниться (сюда скопируется id_rsa.pub)
```

### Альтернативы
| Вариант | Команда | Минусы |
|---------|---------|--------|
| **rsync (сейчас)** | `rsync --archive --chown=deploy:deploy ~/.ssh /home/deploy` | — |
| **cp с chown** | `cp -r ~/.ssh /home/deploy && sudo chown -R deploy:deploy /home/deploy/.ssh` | Два действия вместо одного |
| **ssh-copy-id** | `ssh-copy-id -i ~/.ssh/id_rsa.pub deploy@localhost` | Работает удалённо, но тут мы локально на сервере |
| **Генерировать новую пару на сервере** | `ssh-keygen -t ed25519` прямо на сервере | Ненужно — хотим использовать свой ключ с ноутбука |

### Почему выбран rsync
- **Одна команда:** копирует + меняет владельца + сохраняет права доступа
- **Безопасно:** `--archive` копирует права (chmod 600 на приватный ключ)
- **Идемпотентно:** если запустить дважды — ничего не сломается

### Критично!
Права на приватный ключ должны быть ровно `600` (только хозяин может читать):
```bash
ls -la /home/deploy/.ssh/
# Должно быть:
# -rw------- id_rsa        (600)
# -rw-r--r-- id_rsa.pub    (644)
```

Если права неправильные, SSH падает с "Permission denied".

## Шаг 1.4: Обновление системы

```bash
apt update && apt upgrade -y
```

### Что это делает
1. `apt update` → скачивает свежие списки пакетов из репозиториев
2. `apt upgrade -y` → обновляет установленные пакеты до новых версий

### Альтернативы
| Вариант | Команда | Когда |
|---------|---------|-------|
| **dist-upgrade** | `apt dist-upgrade -y` | Если нужны обновления с удалением конфликтующих пакетов (редко) |
| **Автоматические обновления** | `apt install unattended-upgrades && dpkg-reconfigure unattended-upgrades` | Для production — хорошая идея, но здесь не критично |
| **Пропустить обновления** | Ничего не делать | ❌ Плохо — уязвимости останутся |

### Почему эта стратегия
- **Безопасность:** закрываешь уязвимости в ядре Linux и системных библиотеках
- **Совместимость:** обновления обычно совместимы (особенно `upgrade` vs `dist-upgrade`)
- **Флаг `-y`:** автоматически отвечать "да" на все вопросы (иначе висит и ждёт ввода)

## Шаг 1.5: Установка пакетов

```bash
apt install -y ufw fail2ban git curl nginx
```

### Что это делает
Устанавливает 5 пакетов:

| Пакет | Назначение | Альтернативы | Почему этот |
|-------|-----------|-------------|-----------|
| **ufw** | Firewall | iptables (низкоуровневый), firewalld (systemd) | Просто, понятно, Ubuntu-стандарт |
| **fail2ban** | Защита от brute-force SSH | Denyhosts, sshguard | Популярнейший, легко настраивается |
| **git** | Клонирование репо | Скачать ZIP с GitHub | Нужна полная версионная история |
| **curl** | HTTP-запросы (загрузка файлов) | wget, httpie | Везде установлен, самый совместимый |
| **nginx** | Веб-сервер / reverse proxy | Apache, Caddy, HAProxy | Лёгкий, быстрый, много примеров |

### Альтернативы для веб-сервера
```bash
# Вариант 1: Apache (сейчас выбран nginx)
apt install apache2
# Минусы: тяжелее, конфиг сложнее, для простого proxy не нужен

# Вариант 2: Caddy (новый, умный)
# Плюсы: автоматический HTTPS, конфиг проще
# Минусы: менее popular, меньше примеров

# Вариант 3: Не ставить вообще, пустить Next.js напрямую на порт 80
# Минусы: Next.js как корневой процесс рискованно (один краш — всё падает)
```

### Почему именно эти пакеты
- **ufw:** минимум конфигурации, работает, интегрирован в Ubuntu
- **fail2ban:** критична защита от перебора паролей (даже SSH требует его)
- **git:** клонировать код, обновления — обязательно
- **curl:** загружать установщики и скрипты (частая потребность)
- **nginx:** обязателен для production (даже если сейчас работаешь по IP, потом нужен будет для доменов и TLS)

## Шаг 1.6: Создание Swap (КРИТИЧНО!)

```bash
fallocate -l 4G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
```

### Что это делает
Создаёшь 4-гигабайтный файл на диске, который ОС будет использовать как виртуальное расширение RAM.

**Процесс:**
1. `fallocate -l 4G /swapfile` → выделяешь 4 ГБ на диске
2. `chmod 600 /swapfile` → защищаешь от чтения другими пользователями
3. `mkswap /swapfile` → инициализируешь как swap
4. `swapon /swapfile` → включаешь **сейчас**
5. `echo '...' >> /etc/fstab` → добавляешь в автозагрузку (при перезагрузке включится автоматически)

### Альтернативы

| Вариант | Команда | Минусы |
|---------|---------|--------|
| **Swap через LVM** | `lvcreate -L 4G -n swap vg0 && mkswap /dev/vg0/swap` | Сложнее, нужен LVM на VM |
| **Больше swap (8 ГБ)** | `fallocate -l 8G` | Диск на производительность не влияет, но может помочь при экстремальной нагрузке |
| **Меньше swap (2 ГБ)** | `fallocate -l 2G` | Может не хватить при одновременной сборке Next.js и Docker |
| **Вообще без swap** | Ничего не делать | ❌ **КРИТИЧЕСКАЯ ОШИБКА** — сервер упадёт OOM при сборке |

### Почему именно 4 ГБ

**Потребление памяти:**
- Docker Supabase (10 контейнеров) → ~3 ГБ
- Next.js сборка (`npm run build`) → ~2 ГБ
- **Итого нужно:** ~5 ГБ
- **Доступно на VM:** 8 ГБ
- **Разница:** 3 ГБ

Если оба процесса стартуют одновременно (что редко), может не хватить. Swap в 4 ГБ — подушка безопасности.

**Почему диск, а не чистая RAM:**
- Диск медленнее в 100+ раз, но это всё равно быстрее, чем падение сервера
- Swap работает только при нехватке памяти (не часто)
- В normal situation используется только RAM

### Почему `fallocate`, а не `dd`
```bash
# Вариант 1: fallocate (сейчас)
fallocate -l 4G /swapfile    # Быстро, просто

# Вариант 2: dd (старый способ)
dd if=/dev/zero of=/swapfile bs=1G count=4    # Медленнее в 10+ раз, вписывает реально
```

`fallocate` создаёт файл за миллисекунды (на современных FS), `dd` — за десятки секунд.

### Проверка
```bash
free -h        # Должно показать Swap: 4.0G
swapon -show   # Должно показать /swapfile
```

## Шаг 1.7: Firewall

```bash
ufw allow OpenSSH && ufw allow 80 && ufw allow 443 && ufw --force enable
```

### Что это делает
Открываешь три порта:
- **22 (SSH)** → чтобы ты мог подключиться
- **80 (HTTP)** → чтобы пользователи видели сайт
- **443 (HTTPS)** → чтобы сайт был по HTTPS (потом)

**`--force enable`** включает firewall **сейчас же** (без подтверждения).

### Альтернативы

| Вариант | Команда | Когда |
|---------|---------|-------|
| **Открыть все сразу** | `ufw allow 3000 && ufw allow 8000` (для IP-доступа) | Сейчас — если не хочешь DNS |
| **Белый список IP** | `ufw allow from 192.168.1.100 to any port 3000` | Если доступ только из конкретных мест |
| **Отключить firewall** | `ufw disable` | ❌ Плохо — любой может подобраться к Postgres |
| **iptables напрямую** | `iptables -A INPUT -p tcp --dport 22 -j ACCEPT` | ❌ Сложно, ошибки приводят к потере доступа |

### Почему ufw
- **Простота:** 3 строки вместо 30 для iptables
- **Безопасность:** по умолчанию всё заблокировано (whitelist, не blacklist)
- **Отказоустойчивость:** `--force enable` не блокирует SSH (если бы заблокировал, потерял бы доступ)

### Почему `--force`
Обычно `ufw enable` просит подтверждение (потому что может оборвать SSH). `--force` пропускает подтверждение, потому что мы уже открыли SSH.

## Шаг 1.8: Fail2Ban

```bash
systemctl enable --now fail2ban
```

### Что это делает
- `enable` → запустить при загрузке системы
- `--now` → запустить сейчас же

Fail2Ban мониторит `/var/log/auth.log` и блокирует IP после N неудачных попыток SSH.

### Конфиг по умолчанию
```ini
# В /etc/fail2ban/jail.conf (прочитаешь потом)
[sshd]
enabled = true
port = ssh
filter = sshd
maxretry = 5          # 5 неудачных попыток
findtime = 600        # За 10 минут
bantime = 3600        # Блокировка на 1 час
```

### Альтернативы

| Вариант | Когда | Минусы |
|---------|-------|--------|
| **Пропустить fail2ban** | Если очень упрощать | ❌ Уязвивость к brute-force |
| **Port knocking** | Для экстремальной security | Оверкиль для этого проекта |
| **Отключить SSH вообще** | Только консоль Yandex | Неудобно |

### Почему fail2ban важен
- Постоянные попытки взлома из интернета (ботнеты)
- Fail2Ban автоматически блокирует IP за несколько секунд
- Минимальные resource overhead

## Шаг 1.9: Конфиг SSH (отключение root и паролей)

```bash
nano /etc/ssh/sshd_config
# Найди и измени:
# PasswordAuthentication no
# PermitRootLogin no

systemctl restart ssh
```

### Что это делает
1. **PasswordAuthentication no** → отключить вход по паролю (только SSH-ключи)
2. **PermitRootLogin no** → запретить логиниться как root

### Альтернативы конфигурации

| Вариант | Конфиг | Когда |
|---------|--------|-------|
| **Ключи + deploy** (сейчас) | `PasswordAuthentication no` + `PermitRootLogin no` | ✅ Production-стандарт |
| **Ключи + root** | `PasswordAuthentication no` | Если ты один и не боишься |
| **Ключи + пароли** | Оставить оба включены | Резервный вариант (усложнение) |
| **Только пароли** | По умолчанию | ❌ Уязвивость к brute-force |

### Почему именно эта конфигурация
- **PasswordAuthentication no:** пароль подобрать можно (brute-force), ключ — нет
- **PermitRootLogin no:** даже если кто-то получит ключ, сможет залогиниться только как `deploy`, не как root
- **Принцип layers:** первый слой (ключи), второй слой (не root)

### Важно перед перезагрузкой SSH
**НИКОГДА не рестартуй SSH без проверки!** Если неправильно отредактировать конфиг, потеряешь доступ.

Проверка перед рестартом:
```bash
sshd -t    # Проверяет синтаксис без рестарта
# Если вывод пустой — OK
# Если ошибка — исправь и попробуй снова
```

# БЛОК 2: Docker Engine

## Шаг 2.1: Установка Docker

```bash
curl -fsSL https://get.docker.com | sh
```

### Что это делает
Загружает и выполняет официальный скрипт Docker:
1. Добавляет репозиторий Docker в `apt`
2. Устанавливает Docker Engine, CLI, containerd
3. Настраивает автозагрузку

### Альтернативы

| Вариант | Команда | Когда |
|---------|---------|-------|
| **Официальный скрипт (сейчас)** | `curl -fsSL https://get.docker.com \| sh` | ✅ Рекомендуемый, всегда актуальный |
| **Ubuntu репозиторий** | `apt install docker.io` | Если не доверяешь скриптам (но версия может быть старой) |
| **Podman (вместо Docker)** | `apt install podman` | Если нужна безопасность на уровне контейнеров (для этого оверкиль) |
| **Установка из исходников** | Компилируем из github.com/moby/moby | ❌ Нет смысла |

### Почему официальный скрипт
- Всегда актуальная версия
- Официально поддерживается Docker Inc.
- Добавляет репозиторий (автоматические обновления)
- Работает на всех Linux-дистрибутивах

### Альтернативный способ (без curl)
```bash
# Если curl не установлен (что-то пошло не так)
wget -qO- https://get.docker.com | sh
```

## Шаг 2.2: Добавление deploy в группу docker

```bash
usermod -aG docker deploy
su - deploy
```

### Что это делает
1. Добавляешь `deploy` в группу `docker` (может запускать контейнеры без `sudo`)
2. Переключаешься на пользователя `deploy` (для дальнейшей работы)

### Альтернативы

| Вариант | Команда | Минусы |
|---------|---------|--------|
| **В группу docker** | `usermod -aG docker deploy` | — |
| **Всегда использовать sudo** | `sudo docker ps` везде | Раздражает, каждый раз вводить пароль (но есть NOPASSWD sudoers) |
| **Не давать доступ deploy** | Ничего не делать | ❌ Docker доступен только root (неудобно) |

### Важно!
После `usermod` нужно **переключиться на пользователя** для вступления в силу новой группы:
```bash
su - deploy      # Логиниться как deploy (новая оболочка)
# Или
exec su - deploy # Заменить текущую оболочку
```

Иначе `docker` всё ещё может не работать (группа не обновится в текущей сессии).

### Проверка
```bash
groups     # Должно включать docker
docker ps  # Должно работать без sudo
```

# БЛОК 3: Self-hosted Supabase

## Шаг 3.1: Подготовка каталога

```bash
sudo mkdir -p /opt && sudo chown deploy:deploy /opt
cd /opt
```

### Что это делает
1. Создаёшь каталог `/opt` (стандартное место для приложений)
2. Делаешь `deploy` его владельцем (может писать туда без `sudo`)
3. Переходишь в этот каталог

### Почему `/opt`, а не другие места?

| Путь | Назначение | Почему не там |
|------|-----------|---------------|
| **`/opt`** (выбран) | Приложения третьих сторон | ✅ Стандарт, чист, отделён от системы |
| `/home/deploy/app` | Домашняя папка пользователя | Технически работает, но захламляет домашнюю папку |
| `/srv/` | Данные сервисов | Более для данных, чем для кода |
| `/usr/local/` | Локальные приложения | Обычно для одиночных бинарников, не для больших приложений |
| `/var/www/` | Веб-сайты (Apache, nginx) | Устаревший подход, для этого проекта не подходит |
| `/app` (в корне) | Корень ФС | ❌ Небезопасно, может конфликтовать с системными каталогами |

### Альтернатива: Docker Volumes
Вместо каталога на диске можно использовать Docker Volumes:
```bash
docker volume create supabase-data
docker compose --mount source=supabase-data,target=/var/lib/postgresql
```
**Минусы:** сложнее бэкапировать, сложнее восстанавливать.

## Шаг 3.2: Клонирование репозитория Supabase

```bash
git clone --depth 1 https://github.com/supabase/supabase
mkdir supabase-stack && cd supabase-stack
cp -r ../supabase/docker/* .
cp ../supabase/docker/.env.example .env
```

### Что это делает
1. Клонируешь официальный репо Supabase (флаг `--depth 1` = только последний коммит)
2. Создаёшь папку `supabase-stack` для конкретного экземпляра
3. Копируешь Docker-конфиги и `.env.example`

### Альтернативы клонирования

| Вариант | Команда | Когда |
|---------|---------|-------|
| **Shallow clone (сейчас)** | `git clone --depth 1 ...` | ✅ Быстро, экономит трафик |

## Шаг 3.3: Генерация секретов


### Что это делает
Генерирует 64-символьную случайную строку (32 байта = 64 hex-символа).

### Где использовать каждый секрет

| Номер | Переменная | Использование | Опасность если утечёт |
|-------|-----------|----------------|----------------------|
| **1** | `POSTGRES_PASSWORD` | Пароль для БД | Полный доступ к данным |
| **2** | `JWT_SECRET` | Подпись токенов | Можно подделать любой токен |
| **3** | `SECRET_KEY_BASE` | Шифрование GoTrue | Доступ к сессиям пользователей |
| **4** | `VAULT_ENC_KEY` | Шифрование Vault | Доступ к сохранённым паролям API-ключей |

### Альтернативы генерации

| Вариант | Команда | Когда |
|---------|---------|-------|
| **openssl rand (сейчас)** | `openssl rand -hex 32` | ✅ Стандарт, работает везде |

| **dd** | `dd if=/dev/urandom bs=32 count=1 \| xxd -p -c 32` | ❌ Сложно |
| **Manually** | Сидишь и пишешь 64 символа | ❌ **НИКОГДА** — рискованно, не случайно |

### Почему openssl
- Везде установлен
- Криптографически безопасный источник случайности (`/dev/urandom`)
- Одна команда

### Проверка качества

## Шаг 3.4: Генерация JWT-ключей (ANON_KEY и SERVICE_ROLE_KEY)

### Что это такое
JWT (JSON Web Token) — это закодированные данные, подписанные `JWT_SECRET`. Две роли:
- **ANON_KEY:** для фронтенда, ограниченные права
- **SERVICE_ROLE_KEY:** для бэкенда, обходит RLS (опасный!)

### Структура JWT
```json
// Header (всегда одинаковый для ALIS256)
{
  "alg": "HS256",
  "typ": "JWT"
}

// Payload (разный для каждой роли)
{
  "role": "anon",           // или "service_role"
  "iss": "supabase",
  "iat": 1704067200,        // issued at (сейчас)
  "exp": 9999999999         // expires (через 10+ лет)
}

// Signature
HMACSHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  JWT_SECRET
)
```

### Способ 1: Генератор на сайте (без рисков)

1. Открываешь https://supabase.com/docs/guides/self-hosting#api-keys
2. Вводишь свой `JWT_SECRET`
3. Копируешь два токена (anon и service_role)

**Плюсы:**
- Визуально видишь, что в токене
- Весь процесс в браузере (секрет не отправляется на сервер)

**Минусы:**
- Нужен браузер с интернетом

### Способ 2: Локально через Python

```python
import jwt
import time

secret = "<твой JWT_SECRET>"
now = int(time.time())
exp = now + (365 * 24 * 60 * 60 * 10)  # 10 лет

# ANON_KEY
anon_token = jwt.encode({
    "role": "anon",
    "iss": "supabase",
    "iat": now,
    "exp": exp
}, secret, algorithm="HS256")

# SERVICE_ROLE_KEY
service_token = jwt.encode({
    "role": "service_role",
    "iss": "supabase",
    "iat": now,
    "exp": exp
}, secret, algorithm="HS256")

print(f"ANON_KEY={anon_token}")
print(f"SERVICE_ROLE_KEY={service_token}")
```

**Плюсы:**
- Локально, можно автоматизировать
- Контролируешь даты expiry

**Минусы:**
- Нужен Python и библиотека jwt

### Способ 3: Online JWT Generator

Есть другие сайты типа jwt.io, но их нужно смотреть, потому что некоторые отправляют секрет на сервер.

### Почему два разных ключа

| Где используется | ANON_KEY | SERVICE_ROLE_KEY |
|------------------|----------|-----------------|
| **Фронтенд (браузер)** | ✅ Видна всем | ❌ Никогда! |
| **Server Actions / API** | ❌ Ненужна | ✅ Только здесь |
| **Права доступа** | Ограничены RLS | Обходит RLS |
| **Опасность если утечёт** | Ограничена RLS | КРИТИЧНА — полный доступ |


Найди секции `db` и `studio`, измени `ports`:

```yaml

  ports:
    - "5432:5432"

studio:
  ports:
    - "3000:8000"

# ПОСЛЕ (безопасно)
db:
  ports:
    - "127.0.0.1:5432:5432"

studio:
  ports:
    - "127.0.0.1:3000:8000"    # Если вообще Studio нужен, то только локально
```

### Что это делает
Привязывает порты **только** к localhost (127.0.0.1), поэтому снаружи (из интернета) никто не может подключиться.

### Почему это критично

| Конфиг | Снаружи видно | Опасность |
|--------|---------------|-----------|
| **`5432:5432`** | Postgres | Хакер может подключиться и украсть данные |
| **`3000:8000`** | Studio | Хакер может управлять БД, создавать аккаунты |
| **`127.0.0.1:5432:5432`** | Ничего | Безопасно |

### Альтернативы

| Вариант | Синтаксис | Когда |
|---------|-----------|-------|
| **127.0.0.1 (сейчас)** | `127.0.0.1:5432:5432` | ✅ Только локально |
| **0.0.0.0** | `0.0.0.0:5432:5432` | ❌ Видно из интернета |
| **Вообще закрыть** | Не открывать порт | Если управлять БД только через Docker CLI |

# БЛОК 8: Бэкапы (ОБЯЗАТЕЛЬНО!)

## Что где лежит (инвентарь для пересборки VM)

Ничего из перечисленного **не хранится в git** — это состояние сервера. При
переезде на новую машину всё это создаётся заново по шагам ниже.

| Путь | Что это | Откуда взять заново |
|------|---------|---------------------|
| `/usr/local/bin/pg-backup.sh` | Скрипт бэкапа | Шаг 8.1 (ниже) |
| `sudo crontab -l` (root) | Расписание бэкапов | Шаг 8.2 |
| `/var/backups/supabase/` | Сами бэкапы | Создаётся скриптом |

| `/opt/app/.env.local` | **Секреты приложения** | Только из вашего пароль-менеджера |

## Шаг 8.1: Скрипт бэкапирования

```bash
sudo tee /usr/local/bin/pg-backup.sh >/dev/null <<'EOF'
#!/bin/bash
set -euo pipefail

DIR=/var/backups/supabase
STAMP=$(date +%F-%H%M)
COMPOSE=/opt/supabase-stack/docker-compose.yml
WITH_STORAGE=${1:-}

mkdir -p "$DIR"

docker compose -f "$COMPOSE" exec -T db pg_dumpall -U postgres \
  | gzip > "$DIR/db-$STAMP.sql.gz"

# Целостность архива — необходимое, но не достаточное условие.
gzip -t "$DIR/db-$STAMP.sql.gz"

# pg_dumpall дописывает трейлер только при успешном завершении. Без этой
# проверки оборванный дамп выглядит как валидный gzip нужного размера.
if ! gzip -dc "$DIR/db-$STAMP.sql.gz" | tail -3 | grep -q 'dump complete'; then
  echo "BACKUP FAILED: dump truncated ($STAMP)" >&2
  mv "$DIR/db-$STAMP.sql.gz" "$DIR/BROKEN-db-$STAMP.sql.gz"
  exit 1
fi

# Дамп БД ~85 КБ — 30 копий стоят 3 МБ, держим месяц.
find "$DIR" -name 'db-*.sql.gz' -mtime +30 -delete

# Файлы материалов — 200+ МБ на архив и меняются редко: раз в неделю, 5 копий.
if [ "$WITH_STORAGE" = "--with-storage" ]; then
  tar czf "$DIR/storage-$STAMP.tar.gz" -C /opt/supabase-stack/volumes storage
  find "$DIR" -name 'storage-*.tar.gz' -mtime +35 -delete
fi

echo "backup ok: $STAMP${WITH_STORAGE:+ (+storage)}"
EOF

sudo chmod +x /usr/local/bin/pg-backup.sh
```

### Почему проверок две, а не одна

`pg_dumpall | gzip` без `set -o pipefail` **не падает**, если `pg_dumpall` умер
на середине: `gzip` честно упакует обрезанные данные, файл будет валидным
архивом и `gzip -t` пройдёт. Отличает полный дамп от оборванного только
последняя строка `-- PostgreSQL database cluster dump complete`, которую
`pg_dumpall` пишет при успешном завершении. Битый файл переименовывается в
`BROKEN-*` — чтобы его нельзя было принять за годный бэкап — и **не удаляется**
ротацией: он остаётся как сигнал, что что-то сломалось.

### Почему БД и файлы разведены по расписаниям

|  | Размер | Как часто меняется | Цена потери недели |
|--|--------|--------------------|--------------------|
| Дамп БД | ~85 КБ | постоянно (занятия, оценки, попытки) | высокая |
| Архив storage | ~211 МБ | редко (только при загрузке материала) | низкая |

Одно расписание на двоих означало бы либо 3 ГБ в месяц ради данных, которые не
меняются, либо потерю до недели занятий и оценок. Отсюда: БД — ежедневно
(30 копий = 3 МБ), файлы — по воскресеньям (5 копий ≈ 1 ГБ).

### Структура бэкапов
```
/var/backups/supabase/
├── db-2026-08-15-0317.sql.gz        # БД — ежедневно, хранится 30 дней
├── db-2026-08-14-0317.sql.gz
├── storage-2026-08-16-0317.tar.gz   # Файлы — по воскресеньям, 35 дней
└── BROKEN-db-*.sql.gz               # если появился — бэкап падал, разбираться
```

### Альтернативы

| Вариант | Минусы |
|---------|--------|
| **pg_dumpall + tar (сейчас)** | — |
| **Snapshots диска Yandex Cloud** | Привязаны к диску (не помогут если весь диск скомпрометируют) |
| **S3/облако** | Усложнение (нужен бакет S3) |
| **Вообще без бэкапов** | ❌ Личные данные учеников! Сгорит диск → всё потеряется |

## Шаг 8.2: Расписание (cron)

Сначала **прогнать руками** — оба режима:

```bash
sudo /usr/local/bin/pg-backup.sh
sudo /usr/local/bin/pg-backup.sh --with-storage
sudo ls -lh /var/backups/supabase/
```

Скрипт, чей первый настоящий запуск случается ночью без свидетелей, — это
способ узнать через месяц, что бэкапов нет.

Затем расписание. **Добавлять, а не перезаписывать:**

```bash
sudo crontab -l 2>/dev/null
( sudo crontab -l 2>/dev/null; \
  echo "17 3 * * 1-6 /usr/local/bin/pg-backup.sh >> /var/log/pg-backup.log 2>&1"; \
  echo "17 3 * * 0 /usr/local/bin/pg-backup.sh --with-storage >> /var/log/pg-backup.log 2>&1" ) \
  | sudo crontab -
sudo crontab -l
```

`echo "…" | sudo crontab -` (без `crontab -l` в начале) **затирает** весь
crontab root-а. Если там уже что-то было — оно исчезнет молча.

**Формат cron:** `минута час день месяц день_недели команда`
```
17 3 * * 1-6 /usr/local/bin/pg-backup.sh
 ↓ ↓ ↓ ↓  ↓
 │ │ │ │  └─ день недели: 1-6 = пн–сб, 0 = вс
 │ │ │ └──── месяц (1-12) → * = каждый
 │ │ └────── день месяца (1-31) → * = каждый
 │ └──────── час (0-23) → 3 = 3 утра
 └────────── минута (0-59) → 17
```

### Проверка на следующий день

```bash
cat /var/log/pg-backup.log      # ждём строку "backup ok: …"
ls -lh /var/backups/supabase/
```

Пустой лог — cron не запустился (проверить `sudo crontab -l` и
`systemctl status cron`). Строка `BACKUP FAILED` — дамп оборвался, рядом лежит
`BROKEN-*`.

## Шаг 8.3: Вывезти бэкапы и секреты с сервера

### SSH-доступ с ноутбука

Облачный провайдер выдаёт ключ с нестандартным именем (например
`~/.ssh/ssh-key-1786181586170`), а `ssh`/`scp` без настройки пробуют только
`id_rsa`/`id_ed25519` — отсюда `Permission denied (publickey)` при `scp`, хотя
`ssh` «вроде работает» (там ключ указывался руками). Прописать один раз:

```bash
cat >> ~/.ssh/config <<'EOF'

Host tutor
  HostName <YOUR_IP>
  User <ваш_облачный_логин>
  IdentityFile ~/.ssh/ssh-key-XXXXXXXXXX
EOF
chmod 600 ~/.ssh/config
```

После этого работают `ssh tutor`, `scp tutor:…`, `rsync … tutor:…`.

### Бэкапы

`/var/backups/supabase` принадлежит root (cron работает от него), поэтому
обычный rsync упрётся в права:

```bash
# На ноутбуке периодически:
rsync -avz --rsync-path="sudo rsync" tutor:/var/backups/supabase/ ~/backups/tutor/
```

### Секреты (важнее бэкапов)

`.env`-файлы **не входят** ни в один бэкап и не лежат в git. Без них дамп БД
бесполезен: поднять стек будет нечем. Забрать и положить в пароль-менеджер:

```bash
ssh tutor "sudo cat /opt/supabase-stack/.env" > ~/supabase-prod.env
ssh tutor "sudo cat /opt/app/.env.local"       > ~/app-env.local
```

Перенести содержимое в пароль-менеджер и **удалить локальные копии**
(`shred -u ~/supabase-prod.env`; на macOS `rm -P`). Файл с секретами в домашней
папке рано или поздно уедет в iCloud/Time Machine.

Что именно ломается при потере:

| Переменная | Последствие |
|------------|-------------|
| `POSTGRES_PASSWORD` | Нет доступа к БД, весь стек не поднимется |
| `JWT_SECRET` | `ANON_KEY`/`SERVICE_ROLE_KEY` перестают валидироваться |
| `SERVICE_ROLE_KEY` | Восстановим из `JWT_SECRET`, но вручную |
| `SECRET_KEY_BASE` | Ломаются сессии GoTrue |
| `VAULT_ENC_KEY` | Пулер не читает свои данные (пересоздаётся, наименее критично) |

### Почему нельзя хранить бэкапы на одном диске
Если диск сгорит (hardware fail, хакер удалит), бэкапы тоже пропадут.

**Правило 3-2-1:**
- 3 копии данных
- На 2 разных носителях
- 1 копия вне локации

**Реализация:**
- **Копия 1:** данные на сервере
- **Копия 2:** автоматические бэкапы Yandex (snapshots диска)
- **Копия 3:** ручные бэкапы на ноутбуке (вне сервера)

### Альтернативы

| Вариант | Когда |
|---------|-------|
| **rsync на ноутбук (сейчас)** | ✅ Просто, надёжно |
| **S3 (Yandex Object Storage)** | Если много бэкапов |
| **Telegram-бот** | Если очень мало бэкапов |

## Шаг 8.4: Проверка восстановления (КРИТИЧНО!)

Бэкап, который никогда не восстанавливали — это не бэкап, это мусор. Но
наивный `gzip -dc dump.sql.gz | psql -U postgres` на образе `supabase/postgres`
даёт **~849 ошибок** и восстанавливает данные лишь частично (без `auth.users` —
то есть без единого аккаунта). Ниже — процедура, проверенная 15 августа 2026 на
реальном дампе; она восстанавливает всё: 3 аккаунта, профили, темы, материалы,
вопросы, storage-метаданные, RLS-политики, enum `question_type` с `multiple_choice`,
функции и security-view.

Три грабли, из-за которых наивная команда не работает:

1. **Восстанавливать нужно под `supabase_admin`, а не `postgres`.** В образе
   `supabase/postgres` суперпользователь — `supabase_admin`; `postgres` обычная
   роль без прав на схемы `auth`, `storage`, `realtime`. Под `postgres` половина
   дампа падает на `permission denied for schema auth` и т.п.
2. **Схему `auth` в образе нужно сначала снести.** Образ создаёт свою (старую)
   версию таблицы `auth.users`, дамп же несёт версию, мигрированную GoTrue.
   `CREATE TABLE auth.users` отклоняется как «already exists», `COPY` падает на
   отсутствующих колонках (`is_sso_user`), а за ним по FK рушатся `identities`,
   `sessions`, `profiles`. Лечится одним `drop schema if exists auth cascade;`
   **только для `auth`** — `public`/`storage` ронять нельзя, снесёт расширения.
3. **Оставшиеся ~36 ошибок `... already exists` — норма.** Это объекты, которые
   образ создаёт при инициализации (роли, event-триггеры, publication). Данные
   они не затрагивают.

### Тестовое восстановление (в одноразовый контейнер)

```bash
# 1. Одноразовый Postgres той же версии, что на проде (без -p: наружу не торчит)
docker run -d --name restore-test \
  -e POSTGRES_PASSWORD=testonly \
  supabase/postgres:17.6.1.136
sleep 25 && docker exec restore-test pg_isready -U postgres

# 2. Снести конфликтующую auth-схему образа
docker exec -i restore-test psql -U supabase_admin -d postgres \
  -c "drop schema if exists auth cascade;"

# 3. Восстановить дамп ПОД supabase_admin
gzip -dc db-2026-08-15-0836.sql.gz \
  | docker exec -i restore-test psql -U supabase_admin -d postgres \
  > restore.log 2>&1

# 4. Сколько ошибок и каких (ожидаем ~36, все "already exists")
grep -c '^ERROR' restore.log
grep '^ERROR' restore.log | sed -E 's/"[^"]*"/"X"/g' | sort | uniq -c | sort -rn
```

### Проверка, что данные на месте

```bash
docker exec restore-test psql -U supabase_admin -d postgres -c "
  select 'auth.users' t, count(*) from auth.users
  union all select 'profiles', count(*) from public.profiles
  union all select 'topics', count(*) from public.topics
  union all select 'materials', count(*) from public.materials
  union all select 'questions', count(*) from public.questions
  union all select 'storage.objects', count(*) from storage.objects
  union all select 'rls_policies',
    count(*) from pg_policies where schemaname='public';"

# аккаунты и роли
docker exec restore-test psql -U supabase_admin -d postgres -c \
  "select u.email, p.role from auth.users u
   left join public.profiles p on p.id=u.id order by 1;"
```

Числа должны совпасть с продом (сверять через
`docker compose exec -T db psql -U postgres -c "…"` на сервере).
**`auth.users` = 0 — провал**: данные есть, а войти некому.

### Уборка

```bash
docker rm -f restore-test
```

### Настоящее восстановление на прод (аварийное)

Те же шаги, но целевой контейнер — рабочий `supabase-db`, и **перед** этим:
сделать свежий дамп текущего (пусть и битого) состояния, остановить приложение
(`sudo systemctl stop tutor-web`), чтобы никто не писал в БД во время наката.
После восстановления — `notify pgrst, 'reload schema';` и `systemctl start tutor-web`.
Файлы материалов восстанавливаются отдельно из `storage-*.tar.gz`
(`tar xzf … -C /opt/supabase-stack/volumes`), иначе в `storage.objects` будут
ссылки на файлы, которых нет на диске.

# 🔁 БЛОК 9: Обновление работающего сервера

Блоки 1–8 — это разовая установка. Дальше каждый деплой выглядит так.
Раздел написан по итогам реального обновления (фича `multiple_choice`,
15 августа 2026), где половина шагов оказалась неочевидной.

## Шаг 9.0: Зайти под `deploy`

```bash
ssh <ваш_логин>@<YOUR_IP>
sudo -i -u deploy
```

Облачный провайдер даёт свой логин (например `xqrmztvkap`), но сервер собран
вокруг пользователя `deploy`: ему принадлежат `/opt/app` и `/opt/supabase-stack`,
он в группе `docker`, под ним работает systemd-юнит, и только он может читать
`/opt/app/.env.local` (права `600`).

**Первая команда после SSH — всегда `sudo -i -u deploy`.** Иначе каждая команда
требует `sudo`, а Supabase CLI падает с `failed to read environment file: .env.local`:
он читает `.env.local` для подстановок `env(...)` из `supabase/config.toml`.

Права на `.env.local` ослаблять нельзя — там `SUPABASE_SERVICE_ROLE_KEY`,
обходящий RLS на данных всех учеников.

## Шаг 9.1: Бэкап ДО миграций

```bash
mkdir -p ~/backups
cd /opt/supabase-stack
docker compose exec -T db pg_dumpall -U postgres | gzip > ~/backups/db-$(date +%F-%H%M).sql.gz
```

Проверять обязательно, причём двумя разными проверками:

```bash
gzip -t ~/backups/db-*.sql.gz && echo "архив цел"
gzip -dc ~/backups/db-*.sql.gz | tail -3
```

Последняя строка дампа должна быть `-- PostgreSQL database cluster dump complete` —
её `pg_dumpall` пишет только при успешном завершении.

**Почему мало `gzip -t`:** в конвейере `pg_dumpall | gzip` без `set -o pipefail`
падение `pg_dumpall` на середине не роняет команду. `gzip` честно упакует
обрезанные данные, файл будет валидным архивом и проверку целостности пройдёт —
а половины таблиц в нём не окажется. Строка-трейлер отличает полный дамп
от оборванного.

Сверить содержимое дампа с живой БД:

```bash
gzip -dc ~/backups/db-*.sql.gz | awk '
  /^COPY public\./ { t=$2; n=0; next }
  t && /^\\\.$/    { print t, n; t=""; next }
  t                { n++ }'

docker compose exec -T db psql -U postgres -c "
  select 'profiles' t, count(*) from profiles
  union all select 'topics', count(*) from topics
  union all select 'materials', count(*) from materials
  union all select 'questions', count(*) from questions;"
```

Числа должны совпасть.

## Шаг 9.2: Строка подключения к БД

Порт Postgres **не опубликован на хост**. В `docker compose ps` у сервиса `db`
стоит `5432/tcp` без `0.0.0.0:...->`: это значит «порт открыт внутри docker-сети»,
а не «доступен с хоста». Поэтому:

- `docker compose exec -T db psql …` работает всегда — команда выполняется **внутри** контейнера;
- `--db-url …@127.0.0.1:5432…` падает с `ECONNREFUSED` — на хосте там никто не слушает.

Supabase CLI ходит по TCP с хоста, поэтому ему нужен адрес контейнера:

```bash
DB_CID=$(docker compose -f /opt/supabase-stack/docker-compose.yml ps -q db)
DB_IP=$(docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}} {{end}}' "$DB_CID" | awk '{print $1}')

export DB_URL="postgresql://postgres:$(grep -oP '^POSTGRES_PASSWORD=\K.*' /opt/supabase-stack/.env)@$DB_IP:5432/postgres?sslmode=disable"
```

Два обязательных момента:

- **`?sslmode=disable`** — self-hosted Postgres работает без SSL, а CLI требует TLS
  для любого хоста кроме localhost и падает с `The server does not support SSL connections`.
  Шифровать нечего: трафик идёт по docker-мосту внутри одной машины.
- **IP контейнера меняется** при пересоздании стека — выводить `$DB_URL` заново
  каждую сессию, не сохранять в файл.

Пароль подставляется из `.env`, чтобы не оседать в истории shell. В ошибках CLI
может советовать «Network Restrictions» и ссылку на дашборд supabase.com — это
текст для облачных проектов, к self-hosted он отношения не имеет.

## Шаг 9.4: Если история миграций пуста

Схему можно применить и напрямую через `psql` — тогда таблицы в БД есть,
а `supabase_migrations.schema_migrations` не существует. Проверить:

```bash
docker compose -f /opt/supabase-stack/docker-compose.yml exec -T db psql -U postgres -c \
  "select version from supabase_migrations.schema_migrations order by version;"
```

Если таблицы нет — **`supabase db push` запускать нельзя**: CLI решит, что не применено
ничего, и попробует прогнать все миграции с нуля по заполненной базе. Упадёт на
`relation already exists` где-то в середине, оставив схему в промежуточном состоянии.

Порядок восстановления:

1. Применить недостающую миграцию вручную:

   ```bash
   docker compose -f /opt/supabase-stack/docker-compose.yml exec -T db \
     psql -U postgres -d postgres -v ON_ERROR_STOP=1 \
     < /opt/app/supabase/migrations/<файл>.sql
   ```

   `ON_ERROR_STOP=1` обязателен — без него psql проглотит ошибку и пойдёт дальше.
   `--single-transaction` здесь не нужен: `alter type … add value` спокойнее
   коммитится отдельным оператором.

2. Отметить **все** миграции применёнными, не выполняя их:

   ```bash
   cd /opt/app
   supabase migration repair --status applied \
     20260730000001 20260730000002 … <все версии> \
     --db-url "$DB_URL"
   ```

   `repair` только пишет историю. Он же создаёт схему `supabase_migrations`
   в том виде, какой ожидает CLI, — руками эту таблицу заводить не надо.

3. Убедиться, что расхождений нет:

   ```bash
   supabase db push --db-url "$DB_URL"   # → Remote database is up to date
   ```

## Шаг 9.5: Логи

## Архитектура: один VPS vs App Platform + отдельный VPS

**Выбран:** один VPS (всё вместе)

| Критерий | Один VPS | App Platform + VPS |
|----------|----------|-------------------|
| **Стоимость** | ~200-300 руб/мес | ~500+ руб/мес |
| **Сложность** | Проще | Сложнее (две точки обслуживания) |
| **Производительность** | Лучше (нет сетевой задержки) | Хуже (трафик между сервисами) |
| **Масштабируемость** | Хуже | Лучше |
| **Надёжность** | Одна точка отказа | Две точки отказа |

**Вывод:** для одного репетитора и десятков учеников — один VPS дешевле и проще.

---

## Firewall: ufw vs iptables vs firewalld

**Выбран:** ufw

| Критерий | ufw | iptables | firewalld |
|----------|-----|----------|-----------|
| **Сложность** | Простая | Низкоуровневая | Средняя |
| **Нужна ручная конфигурация** | Нет | Да | Да |
| **Риск потери доступа** | Минимален | Высокий | Средний |
| **Популярность на Ubuntu** | ✅ Стандарт | ❌ Редко | ❌ Редко |

**Вывод:** ufw — стандарт на Ubuntu, просто, безопасно.

---

## Сохранение бэкапов: на сервере vs облако vs локально

**Выбран:** на сервере + вывоз на ноутбук (правило 3-2-1)

| Хранилище | Плюсы | Минусы |
|-----------|-------|--------|
| **На сервере** (Вариант 1) | Автоматично | Сгорит если диск упадёт |
| **S3/облако** (Вариант 2) | Безопасно | Платные, ещё один сервис |
| **На ноутбуке** (Вариант 3) | В отдельной локации | Нужно вывозить руками |
| **Все три (3-2-1)** (выбран) | Максимальная защита | — |

**Вывод:** даже простой `rsync на ноутбук` раз в неделю лучше, чем ничего.
