# CLAUDE.md — БиоПодготовка

## О проекте
Веб-платформа поддержки персональных занятий по биологии для подготовки к ЕГЭ/ОГЭ.
Один репетитор, ученики (десятки, не тысячи). Два интерфейса: кабинет ученика и кабинет репетитора.

Основной принцип продукта: репетитор загружает материалы и создаёт план уроков один раз,
а для каждого ученика только назначает занятия/тесты — минимум ручной работы на нового ученика.

## Стек
- **Frontend + Backend:** Next.js (App Router, TypeScript). Отдельного бэкенд-сервера нет —
  чтение данных через Server Components, изменения через Server Actions.
- **БД + Auth + Storage:** Supabase, **self-hosted** (Docker Compose).
  Причина self-hosted, а не облачный Supabase: 152-ФЗ — персональные данные учеников (граждан РФ)
  должны храниться на серверах в РФ.
- **Хостинг:** Timeweb Cloud — App Platform для Next.js (SSR) + отдельный VPS под self-hosted Supabase.
- **Стили:** Tailwind CSS (дефолт для Next.js-проектов, хорошо ложится на генерацию кода Claude Code).
  Если это не то, что нужно — легко поменять на старте, конкретных компонентов ещё не писали.

## Роли и авторизация
- Две роли: `student`, `tutor`.
- Роль хранится в таблице `profiles`, 1:1 к `auth.users` (Supabase Auth отвечает за саму аутентификацию).
- Роутинг разделён на `app/(student)/...` и `app/(tutor)/...` — каждая группа со своим layout
  и проверкой роли в middleware.

## Принципы схемы БД
- **Контент отделён от "экземпляра для ученика":**
  `topics`, `materials`, `questions`, `test_templates`, `courses` — создаются один раз.
  `student_lessons`, `student_test_attempts` — записи конкретного ученика (тема, дата,
  ссылка на созвон, результат).
- **Многие-ко-многим — через junction-таблицы**, не жёсткие связи 1:1:
  `topic_materials` (материалы ↔ темы), `topic_tests` (ДЗ ↔ темы),
  `course_topics` (темы ↔ программы), `test_template_questions` (вопросы ↔ тесты).
- **`topics`** — справочник тем: отдел (`section_id`), уровни (`levels`), код кодификатора.
  Редактируется из интерфейса и тегирует материалы, вопросы и тесты.
- **Прогресс ученика** считается запросом/view поверх `student_answers` + `questions.topic_id`,
  не хранится отдельной таблицей — меньше риска рассинхронизации.
- Гибкие типы — через enum/JSONB (`materials.type`, `questions.options`), а не отдельные таблицы под каждый тип.
- Схема версионируется миграциями в `supabase/migrations/`, TS-типы генерируются командой
  `supabase gen types typescript` — при любом изменении схемы перегенерировать типы.

### Обязательно при добавлении таблицы
**Новой таблице нужен явный `GRANT`.** В актуальном Supabase таблицы в `public` не выдаются
ролям Data API автоматически (см. `auto_expose_new_tables` в `supabase/config.toml`). Без
`grant … to authenticated` любой запрос падает с `permission denied for table …` (код 42501),
даже когда RLS-политики разрешают доступ. Образец — `20260730000003_grants.sql`;
`service_role` покрыт `20260806000007_service_role_grants.sql`. RLS при этом всё равно нужна:
GRANT решает «может ли роль обращаться к таблице», RLS — «какие строки видно».

### Тегирование контента
Три независимые оси у `materials`, `test_templates`, `questions`, `topics`:
- **Отдел** — `section_id` → таблица `sections`, редактируется из интерфейса (без миграций).
- **Уровень** — `levels exam_type[]`, массив: один материал обычно годится и для ОГЭ, и для ЕГЭ.
  Enum `exam_type` переиспользован (`oge` / `ege` / `olympiad`); у контента подпись «Уровень»,
  у ученика — «Экзамен».
- **Тема** — `topic_id`; у материалов необязательна, у тестов обязательна (проверяется при импорте).

### Тема — единица плана, занятие — календарная запись
Ключевое: **не занятие, а тема** — то, что переиспользуется. Материалы и ДЗ висят на теме
(`topic_materials`, `topic_tests`), а сколько занятий уходит на тему — свойство конкретного
ученика: несколько `student_lessons` могут ссылаться на одну тему. Один ученик проходит
генетику за урок, другой за три, и это не требует копий шаблонов.

`lesson_templates` со своими junction-таблицами удалены миграцией
`20260806000008_topics_and_courses.sql` — держать и занятие-шаблон, и тему значило бы держать
две конкурирующие единицы плана.

**«Занятие 2 из 3» не хранится в БД** — считается при рендере группировкой занятий ученика
по теме. Сохранённый счётчик разошёлся бы с реальностью после первой правки плана.

### Программы и генерация плана
`courses` — именованные программы под уровень («ЕГЭ годовой», «ЕГЭ интенсив с января»),
`course_topics` — упорядоченные темы с `planned_lessons` (сколько занятий отвести теме).

RPC `generate_plan_for_student(p_student, p_course, p_start, p_interval_days)` создаёт план на
год: занятия по всем темам программы, с датами по указанной периодичности, копируя в каждое
занятие материалы и ДЗ темы. **Идемпотентна:** досоздаёт только недостающее (считает уже
существующие занятия по теме), даты продолжает после последнего занятия, правки и отметки
«проведено» не трогает. Поэтому «Дополнить план по программе» безопасно жать когда угодно —
в том числе после пополнения программы посреди года.

Планы материализованы: правка темы или программы **не** меняет уже созданные занятия.

### Правило видимости
Ученик видит **пройденные** занятия полностью (материалы, ДЗ), у предстоящих — только
название, дату и ссылку на созвон. Держится на RLS, не на вёрстке:
- `student_lesson_materials` / `student_lesson_tests` — только при `status = 'completed'`;
- `materials_select` — ученику только материалы его пройденных занятий (важно: у материала
  может быть `external_url`, а он лежит прямо в строке, поэтому «скрыть в UI» недостаточно);
- `topic_materials` / `topic_tests` — только репетитору: это состав программы, и открыв их
  ученику, мы выдали бы содержимое будущих занятий в обход правила;
- файлы в бакете `materials` закрыты полностью — политик на `storage.objects` нет,
  подписанные ссылки выдаёт сервер через `/api/materials/[id]/open`, где право доступа
  определяет та же RLS.

### Тесты: баллы, проверка, безопасность
- **Балл — число, а не «верно/неверно».** `questions.max_points` (1–10, из поля `points`
  в файле теста), `student_answers.points` — начислено. `is_correct` означает полный балл
  и используется работой над ошибками. Прогресс (`student_topic_progress`) считается
  в баллах: `earned_points` / `max_points`, поэтому 1 из 2 даёт 50%, а не 0.
- **`questions` и верные ответы закрыты от учеников** (`q_select_tutor`). Колоночные GRANT-ы
  не помогли бы: репетитор и ученик — одна роль `authenticated`.
- **Начисление баллов только в БД.** `start_attempt`, `save_answer`, `finish_attempt` —
  `SECURITY DEFINER` (им нужно читать `correct_answer` и `max_points`), поэтому вся
  авторизация в них **явная**: сверка `auth.uid()` с владельцем попытки в каждой функции.
  Правя их, проверяйте права руками — RLS не подстрахует. `review_answer` — только репетитор,
  она же пересчитывает балл и закрывает попытку, когда непроверенных ответов не осталось.
- **Лимит времени — ориентир, а не блокировка.** `save_answer` принимает ответы и после
  истечения (миграция `20260806000010`): наказывать ученика за то, что он думал дольше,
  и терять набранный текст — хуже, чем зафиксировать превышение. «Не уложился»
  вычисляется из `finished_at - started_at` (`lib/tests/attempt.ts`), отдельной колонки
  нет намеренно — она разошлась бы с датами.
- **Вопросы живут только внутри теста.** Отдельного «банка вопросов» в интерфейсе нет:
  он дублировал карточку теста. Поэтому удаление теста удаляет и его вопросы — кроме тех,
  что попали ещё в другой тест (связь many-to-many это допускает).
- **Тесты доступны ученику лишь по темам пройденных занятий** (`tt_select`) — иначе сокрытие
  ДЗ будущего занятия обходилось бы через страницу «Тесты».

### Два view с definer-семантикой — это границы безопасности
`attempt_questions` и `student_topic_progress` созданы с `security_invoker = false`
**намеренно**: им нужно обойти RLS на `questions`, иначе ученик не увидел бы ни вопросов
своей попытки, ни собственного прогресса. Доступ ограничивает их собственный `WHERE`
(`a.student_id = auth.uid() or public.is_tutor()`). Любая правка этих view — правка границы
безопасности; `attempt_questions` вдобавок намеренно не содержит `correct_answer`.

### Грабли PostgREST: неоднозначные связи
После появления `topic_tests` между `test_templates` и `topics` стало **две** связи, и
`topics(...)` в select падает с `Could not embed because more than one relationship was found`.
Указывайте конкретный ключ: `topics!test_templates_topic_id_fkey(title)`. То же самое у
`materials` из-за `topic_materials` — `topics!materials_topic_id_fkey(title)`. Ошибка приходит
в `error`, а `data` при этом `null`: страница, которая молча покажет пустой список, выглядит
как «данных нет», хотя запрос упал. Такие чтения лучше проверять на `error` и падать.

## Референсы дизайна
Кликабельные HTML-мокапы (см. `docs/mockups/`) — ориентир по структуре экранов и UI-паттернам,
провалидированы с репетитором:
- `student_portal.html` — дашборд с прогрессом, план занятий, таблица материалов, тесты с таймером, ошибки
- `tutor_portal.html` — список учеников (карточка: расписание, результаты, контакты, оплата),
  библиотека материалов, планы уроков, банк вопросов/тестов

Палитра: зелёный/янтарный с "клеточными" акцентами (шестиугольники). Шрифты: Source Serif 4 (заголовки) + Inter (текст).
Это рабочий черновик стиля, не финальный визуальный язык — можно пересматривать при вёрстке реальных страниц.

## MVP-скоуп (делаем сейчас)
1. Логин с двумя ролями
2. Профиль/дашборд ученика (прогресс, следующее занятие)

5. Кабинет репетитора: ученики (+ контакты, оплата), материалы, планы уроков, назначение занятий, вопросы/тесты

## Локальный запуск
```bash
supabase start                 # БД, Auth, Storage в Docker
supabase db reset              # применить миграции + seed.sql заново
npm run dev                    # http://localhost:3000
```
Переменные в `.env.local` (значения — из `supabase status`): `NEXT_PUBLIC_SUPABASE_URL`,
`NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`.
Тестовые аккаунты из сида, пароль у всех `password123`: `tutor@bio.local` (репетитор),
`anya@bio.local` (одно занятие пройдено), `petya@bio.local`.

Две грабли, на которые уже наступали:
- **Заводя пользователя напрямую в `auth.users`** (как в `seed.sql`), обязательно заполнять
  `confirmation_token`, `recovery_token`, `email_change_token_new`, `email_change` пустой
  строкой. У них нет `DEFAULT ''`, а GoTrue читает их в Go-строку: на `NULL` вход падает
  с «500: Database error querying schema».
- **Загрузка файлов** требует `experimental.serverActions.bodySizeLimit` в `next.config.ts` —
  по умолчанию тело Server Action ограничено 1 МБ, презентации не пролезают.

## Конвенции (дополнять по ходу разработки)
- Мутации — Server Actions в `actions.ts` рядом со страницей; после записи `revalidatePath`.
- Каждое действие начинается с `requireRole("tutor")`. Service-role клиент
  (`lib/supabase/admin.ts`) — только после этой проверки, он сам ничего не проверяет.
- Русские подписи enum-ов — в `lib/labels.ts`, чтобы формулировки не расползались по экранам.
- **Модалку закрывать после отправки, а не в `onClick`.** Если модалка рендерится условно
  (`{editing && <Modal …>}`), `setState` в обработчике клика размонтирует форму раньше, чем
  браузер выполнит сабмит, — действие молча теряется, кнопка выглядит мёртвой. Обёртка
  `submitThenClose(action, close)` из `components/ui/modal.tsx` закрывает окно после того,
  как Server Action отработал.
- Динамические страницы: `params` и `searchParams` — это Promise (конвенция Next 16).
- Коммиты, форматирование, тесты — пока не зафиксированы, договоримся в процессе.
